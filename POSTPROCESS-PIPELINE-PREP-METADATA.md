# PREP reporting metadata for post-processing

## Purpose

`PREPARE-TIMES-NZ` will publish a small, human-readable CSV metadata contract
for solver post-processing. It describes model processes, commodities, and
timeslices produced by PREP, together with small deterministic lookup
expansions for regular code families. `SOLVE-TIMES-NZ` post-processing will
consume this contract to label and validate result files.

This removes the current pattern where `TIMES-NZ-INTERNAL-QA` rebuilds a model
taxonomy from scattered PREP intermediate files, generic configuration metadata,
code-name parsing, and local patches. It also establishes the intended one-way
dependency:

```text
PREPARE-TIMES-NZ -> reporting metadata -> SOLVE-TIMES-NZ post-processing
                                      -> parquet release -> QA app
```

The artifact directory is generated by PREP and must never be edited manually:

```text
PREPARE-TIMES-NZ/data_intermediate/postprocessing_metadata/
```

CSV is intentional. The artifacts are small, inspectable metadata rather than
large result tables. A JSON manifest is retained for versioning, provenance and
file hashes.

## Ownership boundary

PREP owns model-derived identity: what each actual process and commodity means,
its relationships, units, and timeslice definitions.

SOLVE post-processing owns result interpretation: which result attributes and
flows form published measures such as generation, energy demand, capacity,
emissions, or carbon cost.

The QA app owns presentation only: display wording, UI ordering, charts and
release selection. It must not rebuild model taxonomy, read PREP intermediates,
or infer codes from names.

Result-attribute rules therefore do **not** belong in this PREP metadata
directory. For example, the rule that `VAR_FOut` for an energy commodity is
electricity generation belongs to the solver post-processing package.

## Proposed contract

All CSVs are UTF-8, use stable column order, and are deterministically sorted.
Codes remain strings. Empty optional labels are blank rather than replaced with
invented values.

### Process metadata

Keep process domains separate. A universal process catalog would be sparse and
would make domain-specific requirements conditional: demand devices require
sector/end-use/technology labels, generators require plant labels, and primary
production requires supply classification. The existing separate result outputs
are the right domain boundary, so PREP metadata mirrors them.

| File | Required domain fields in addition to `Process` | Notes |
| --- | --- | --- |
| `process_units.csv` | `ActivityUnit`, `CapacityUnit`, TIMES set | Shared metadata; the only broad process lookup. |
| `demand_processes.csv` | `ProcessGroup`, `CommodityOut`, sector, end-use and technology labels | Includes transport and its explicit `Utilisation` field. |
| `electricity_generation_processes.csv` | `ProcessGroup`, `PlantName`, `TechnologyGroup`, `Technology` | Electricity reporting labels. |
| `primary_production_processes.csv` | imported/domestic, renewable status, fuel group/detail, supply technology labels | Used for primary energy and emissions reporting. |
| `transformation_processes.csv` | `ProcessGroup`, `TransformationGroup`, `TechnologyGroup`, `Technology` | Energy conversion processes such as electrolysers, anaerobic digesters and refineries. Input/output commodities remain in result rows rather than duplicating topology here. |
| `distribution_processes.csv` | process group, sector and carried fuel | A deterministic code-rule lookup may include non-current possible codes. |
| `battery_processes.csv` | technology group and technology/duration | Used by battery-flow and capacity outputs. |
| `technical_processes.csv` | technical group and description | Dummies and closures where they must be reported or excluded. |

Each domain file includes `ClassificationSource` and `ClassificationMethod`
(`Declared`, `RuleGenerated`, or `Exception`). Process keys must be unique
within a file. A process must not appear in incompatible domain files; an
approved multi-domain use needs an explicit exception.

### Commodity metadata

Keep commodity domains separate for the same reason. The files are:

| File | Required fields in addition to `Commodity` | Notes |
| --- | --- | --- |
| `energy_commodities.csv` | `Fuel`, `CommodityGroup` | The fuel/sector cross join is retained as a deterministic `RuleGenerated` lookup. |
| `demand_commodities.csv` | `CommodityGroup`, sector and end-use labels, `Unit` | Used for energy-service demand classification. |
| `emissions_commodities.csv` | `CommodityGroup` | The `TOTCO2` measure rule remains post-processing policy. |
| `currency_commodities.csv` | `CommodityGroup`, description, `Unit` | Finance/reporting codes. |

Each domain file includes `ClassificationSource` and `ClassificationMethod`.
Commodity keys must be unique within a file; overlaps between domains require
an explicit documented reason. Rule-generated lookup rows are safe because
post-processing left-joins them onto existing result rows.

### `timeslices.csv`

One row per model timeslice, including `ANNUAL`.

| Column | Meaning |
| --- | --- |
| `TimeSlice` | Exact TIMES timeslice code. |
| `YearFraction` | Fraction of a year represented by this timeslice; `1` for `ANNUAL`. |
| `TimesliceOrder` | Explicit integer order used by TIMES. |
| `ClassificationSource` | PREP settings/load-curve artifact that supplied the row. |

The explicit order is important: `xl2times==0.3.0` currently preserves the
configured `ALL_TS` order, but reporting consumers should not infer order from
CSV row position or lexical sort.

### `reporting_exceptions.csv`

This file is only for a genuine non-standard case that cannot yet be produced
by normal preparation data. It must be small and explainable.

| Column | Meaning |
| --- | --- |
| `EntityType` | `Process` or `Commodity`. |
| `Code` | TIMES code receiving the exception. |
| `Field` | Catalog field set or overridden by the exception. |
| `Value` | Assigned value. |
| `Reason` | Why normal PREP data cannot supply the value. |
| `Source` | Source, assumption, or decision that justifies it. |

Exceptions are applied by PREP when constructing the domain catalogs; they are
not a second lookup mechanism for downstream consumers.

### `reporting_manifest.json`

The manifest contains:

- contract schema version;
- PREP code revision and configuration identity;
- artifact creation time;
- each CSV filename, SHA-256 hash, columns and row count;
- hashes/identities of source PREP inputs used to create each catalog; and
- validation and coverage results.

Solver post-processing records the manifest path and hash in each parquet
release manifest. That makes a result release traceable without requiring a
copy of every PREP intermediate file.

## Current-source assessment

### Clean or straightforward sources

| Area | Current source | Contract treatment |
| --- | --- | --- |
| Timeslice definitions | `SysSettings.toml` defines Season, Weekly and DayNite order. | Emit `TimesliceOrder` from this declaration. |
| Year fractions | Load-curve processing already produces `YRFR`. | Emit as `YearFraction`, with `ANNUAL = 1`. |
| Process activity/capacity units | Generated process definitions contain `Tact` and `Tcap`. | Resolve once in PREP; do not re-parse generic metadata/TOML downstream. |
| Residential, commercial and agriculture demand | Existing prepared demand tables already have reporting labels. | Consolidate into `demand_processes.csv` and `demand_commodities.csv`. |
| Most industry demand | Existing base/future process definitions carry most labels. | Consolidate, then replace the small `NEWTECH`/EAF patches at source. |
| Base-year electricity | Electricity supply data has process, plant and technology identifiers. | Emit final labels in the electricity PREP writer. |
| Genstack electricity | Genstack data has process, plant and technology identifiers. | Emit final labels in the electricity PREP writer. |
| Offshore wind labels | Current label is a deterministic combination of technology and region. | Compute it in PREP where offshore processes are created. |
| Batteries and demand flex | Their process definitions are generated in PREP, although current reporting maps are static QA files. | Emit identity, technology, duration/flex label and units in PREP. |
| Energy transformation | No dedicated current QA output/concordance exists, but future model processes will need distinct reporting from distribution. | Emit `transformation_processes.csv` when a transformation process is introduced; do not encode it as distribution or primary production. |

### Requires upstream cleanup or an explicit exception

| Area | Current issue | Required treatment |
| --- | --- | --- |
| Transport | QA joins stage-4 data to manual process/commodity maps and repeatedly parses `_LOW`, `_MED`, `_HIGH` from process names. | Emit mode, technology and `Utilisation` in transport preparation. Downstream code must not parse `TechName`. |
| Energy commodities | QA cross-joins fuel and sector code maps, then adds manual distribution exceptions. The cross join is a valid deterministic left-join lookup, but it is hidden in QA. | Move the fuel/sector inputs and cross-join generation into PREP; materialise the mapping with `ClassificationMethod = RuleGenerated`; validate unique commodity keys and exception conflicts. |
| Distribution | QA generates a regular `FTE_<sector><fuel>` lookup, then appends electricity, LNG and IRE special cases. The generated lookup is valid, but its rule and exceptions are hidden in QA. | Move the code-rule generation into PREP; materialise it with `ClassificationMethod = RuleGenerated`; retain explicit exception rows and validate unique process keys and conflicts. |
| Primary production | `production.csv` is a manually maintained QA concordance with no generator. | Add a PREP-owned, source-controlled primary-production reporting mapping with provenance. |
| Emission and finance commodities | Current maps are static QA files; `TOTCO2` has special downstream treatment. | Emit actual commodity identities in PREP; retain measure-specific exclusion rules such as `TOTCO2` handling in post-processing. |
| Dummy and closure processes | Current maps are static QA code lists and may be TIMES technical conventions. | Put model-created codes in PREP catalogs; retain only documented solver technical-code policy where PREP cannot own them. |
| Documentation | QA currently copies generated concordances into PREP documentation. | PREP becomes the sole generator; documentation consumes its generated catalogs. |

## Initial implementation plan

## Current implementation status

PREP now writes the current demand, electricity generation, energy commodity,
distribution, primary production, battery, technical/dummy, emissions,
currency, process-unit and commodity-unit catalogs to
`data_intermediate/postprocessing_metadata/`. The legacy fuel/sector,
electricity-technology, primary-production and technical labels have been
moved unchanged into `data_raw/coded_assumptions/reporting/` so they are owned
and versioned with PREP rather than imported from QA.

The compatibility check confirms identical code coverage for every migrated
legacy catalog other than declaration units. Current PREP declarations differ
from the stored QA unit catalogs (process: 10 old-only and 85 new-only rows;
commodity: 3 old-only and 2 new-only rows), so the eventual solver cut-over
must report those differences rather than treating the stored QA catalogs as a
truth source. `timeslices.csv` is generated from the configured TIMES slice
order and calculated year fractions, with clean component/display labels.
`transformation_processes.csv`, the reporting manifest and final
provenance/overlap validation remain to be implemented.

### 1. Freeze the current behaviour

For representative solved cases, capture the current QA-produced concordance
CSVs and clean-result output schemas, row counts, unmatched-code reports, and
representative result values. Store compact test fixtures and expected
summaries, not large model results. This is the parity baseline.

### 2. Inventory current consumers and fields

List every catalog field read by:

- current post-processing transformations and coverage checks;
- calibration checks and standalone analysis scripts that will remain in this
  repository; and
- the current QA app.

Classify each field as model identity, result interpretation, or presentation.
Only model-identity fields enter the PREP contract. This inventory is the gate
before freezing schemas.

### 3. Add pure catalog builders in PREP

Following the PREP module convention, add dataframe-only builders under
`PREPARE-TIMES-NZ/src/` and make the existing PREP scripts own reads/writes and
orchestration. Do not add a script that independently trawls
`data_intermediate` after the fact.

Begin with the clean sources: timeslices, units, electricity, and non-transport
demand. Build domain rows while the relevant preparation dataframe is already
in hand. Write the domain CSVs and manifest from a single final PREP stage.

### 4. Resolve non-standard domains at the source

Add transport labels to transport preparation. Move the energy and distribution
code-rule inputs and cross-join generation into PREP, retaining the current
simple deterministic rules rather than reconstructing them downstream. Add
explicit, source-controlled mappings for primary production and any unavoidable
technical codes. Every temporary exception needs a reason/source and a removal
criterion.

Do not reproduce untested QA guesses merely to obtain parity. A deterministic
fuel/sector code rule is acceptable when its generated keys are unique, its
exceptions are non-conflicting, and it is tested. Where an old output includes
a code that neither a declared entry, tested rule nor exception can explain,
fail coverage validation and make the missing classification explicit.

### 5. Validate the PREP contract

Add small unit tests using fake dataframes for:

- required columns and stable schemas;
- unique process and commodity codes within each domain;
- no unintended overlap between incompatible process/commodity domains;
- required labels/units for each domain;
- non-negative timeslice fractions, one `ANNUAL` row, and intended order;
- unique rule-generated commodity/process keys and no conflicts with declared
  or exception entries;
- exception provenance and no duplicate/conflicting exception assignments; and
- coverage of process/commodity codes in the frozen representative baseline.

Add an integration-level PREP run check that writes the artifact directory and
manifest. Generated `data_intermediate` artifacts remain untracked.

### 6. Compare and cut over incrementally

Refactor one post-processing output family at a time to read its new domain
CSVs:

1. timeslice-derived outputs;
2. electricity generation and demand;
3. energy-service demand, capacity, and energy transformation when introduced;
4. transport, primary energy, emissions and technical outputs.

For each family, compare schema, row count, labels and representative values
against the frozen baseline. Remove its old QA concordance builder/patch only
after parity is accepted and the relevant PREP domain files have complete
coverage.

### 7. Hand off to solver post-processing

After all required output families use the contract, move the result reader,
transformations, validation, and parquet release writer into
`SOLVE-TIMES-NZ`. The solver post-processor accepts a completed solver-run
directory and a PREP metadata directory, validates `reporting_manifest.json`,
and records its hash in the release manifest.

## Completion criteria

- PREP produces deterministic, contract-valid domain metadata files from its
  ordinary pipeline.
- Every code used by supported post-processing output is catalogued by a
  declared entry, a tested deterministic rule, or a documented technical
  exception.
- No post-processing code reads arbitrary PREP stage files, generic config
  metadata, or QA-local concordances to identify model codes.
- New outputs match the approved baseline, or each intentional difference is
  documented and accepted.
- The parquet release manifest pins the exact PREP reporting manifest used.

## Non-goals

- Replacing GDX2VEDA or changing raw solver-result format.
- Making PREP metadata a general-purpose data warehouse.
- Moving UI presentation labels or Shiny deployment configuration into PREP.
- Exporting full model topology: raw result rows already identify their process
  and commodity, while `TOP` remains an existing solver/DD concern. Add a
  topology artifact only if a future post-processing rule demonstrates a need.
- Solving every historical taxonomy inconsistency before the first contract;
  exceptions are allowed when documented and validated.
