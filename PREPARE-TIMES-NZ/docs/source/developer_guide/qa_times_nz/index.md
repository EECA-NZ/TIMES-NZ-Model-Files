# QA-TIMES-NZ

`QA-TIMES-NZ` is designed to compare the results of two scenarios and outputs a shareable report as a single HTML file. It's designed to assess the differences between two model runs and summarise these, while also providing reasonable underlying detail. 

It uses summary files produced by `SOLVE-TIMES-NZ` postprocesing. New data, aggregations, or tidying should always be done in `SOLVE` postprocessing so the results are available downstream for any other consumers (like `QA-TIMES-NZ`, or one-off studies). This means that the summary results are held and stored between different scenario solves or published releases, allowing easy tracking. 

The report is designed to read either individual scenarios packaged as releases in `PUBLISH`, or individual scenarios found in `SOLVE`, as appropriate. 

**Requirements**: run `uv sync --all-groups` just in case, and ensure that you have scenario results generated by `SOLVE-TIMES-NZ` or packaged by `PUBLISH-TIMES-NZ`.

## Generate a report

From the repository root:

```bash
uv run qa-times-nz generate_qa
```

The command prints the resolved baseline and candidate, then writes two files inside `QA-TIMES-NZ/build/`:

| File | Contents |
| --- | --- |
| `TIMES-QA-<baseline label> vs <candidate label>.html` | The report. It is self-contained (charts are embedded), so recipients can open it offline without Python or the repository. |
| `TIMES-QA-<baseline label> vs <candidate label> comparisons.csv` | The same values in long form for Excel or other tools: baseline, candidate, difference, percentage change and tolerance result for every row. |

Reports with the same labels are overwritten each run, and is not an artefact we currently store. Both files are Git-ignored.

## Choose what to compare

The inputs are set in `QA-TIMES-NZ/report_config.toml`. It has a `tolerance` and two sections, `baseline` and `candidate`. Each section selects a `RELEASE` or a `SOLVE` run independently of the other.

For example

```toml
tolerance = 0.05

[baseline]
source = "RELEASE"
release = "v308"
scenario = "steady-v308"
label = "Steady v308"

[candidate]
source = "SOLVE"
scenario = "steady"
label = "Steady development"
```

| Field | `source = "RELEASE"` | `source = "SOLVE"` |
| --- | --- | --- |
| `scenario` | Required. Exact scenario ID in the release manifest, such as `steady-v308`. | Required. Scenario case name, such as `steady`. |
| `release` | Required. Release directory name under `PUBLISH-TIMES-NZ/releases/`. | Not allowed. |
| `timestamp` | Not allowed. | Optional. Pins a run (see below). |
| `label` | Optional display name for the report. | Optional display name for the report. |

Use the exact identifiers, including case: `steady` is a SOLVE case name, while
`Steady` is only a label. Labels never select results. Unknown fields, or fields
belonging to the other source type, are rejected.

`tolerance` is a relative fraction. `0.05` flags any annual value that differs
from the baseline by more than 5% of the baseline value.

### How a SOLVE run is selected

SOLVE runs are found under `SOLVE-TIMES-NZ/build/solves/`.

- **No `timestamp`:** QA uses the most recently completed run of that case at
  the current workspace version (the version in the root `pyproject.toml`).
  "Most recent" is the run manifest's `execution.completed_at`, not file
  modification times. Failed or unfinished runs are ignored, and two runs with
  the same latest completion time are an error.
- **With `timestamp`:** QA uses exactly that run, even if it is from an older
  version. The timestamp is the UTC token in the run directory name. For
  `steady-v3.0.9-20261112T074405Z` it is `20261112T074405Z`. A pinned run that
  is missing, incomplete or ambiguous is an error; QA never falls back to
  another run.

Latest selection can change between reports as new solves finish. The command
prints the exact run it selected, so copy that timestamp into the configuration
whenever you need to repeat the comparison. For two development solves, pin at
least the baseline.

Whichever way a run is selected, it must have both execution and
post-processing marked complete, with every declared output present, including
the prepared summary CSVs. Missing outputs are an error even when a run says it
completed.

### Use a personal configuration

You can mess around with the report config by creating `report_config_dev.toml`, which is git-ignored. You can create this file yourself, or run `uv run qa-times-nz init-dev-config` to create it by copying the main config file. 

This allows you to run a bunch of tests without messing with the "standard" report config, which is shared across the repo. The QA report will use the dev config if using a `--dev` paramater like: 

```bash
uv run qa-times-nz generate_qa --dev
```

`init-dev-config` copies the main configuration and refuses to overwrite an existing developer file. `report_config_dev.toml` is Git-ignored. Developer runs write to the same `build/` files as main runs. 

### Errors you may see

Invalid input stops the run before any output is written.

| Message (abridged) | Usual cause |
| --- | --- |
| `Missing QA configuration ... init-dev-config` | `--dev` used before creating the developer file. |
| `Expected ... and optional ...` | A field is missing, unknown or belongs to the other source type. |
| Run/release not found, ambiguous or incomplete | Check the release name, the SOLVE case, the timestamp, and that post-processing finished. |
| `Expected ... in <unit>`, `Duplicate metric keys`, `Missing metric fields` | A summary CSV does not have the shape the report expects. Check the SOLVE summary. |

## How the code is organised

```
QA-TIMES-NZ/
  report_config.toml          # shared input selection
  src/qa_times_nz/
    cli.py                    # qa-times-nz commands
    report_inputs.py          # config validation, release/run selection, summary reading
    report/
      metrics.py              # which metrics appear on which page
      compare.py              # read_metric, period_comparison, tolerances
      charts.py               # SVG charts
      render.py               # HTML tables and page layout
      build.py                # build_report: orchestrates, writes HTML and CSV
      assets/                 # report.css, report.js
  tests/
```

Dependencies run one way: `build` uses `render`, which uses `charts`, which
uses `compare`. `compare` contains the checking logic and knows nothing about
HTML, so it is easy to test with small fake tables.

## Add a metric to the report

1. **Make sure SOLVE writes the summary.** Per-scenario calculations belong in
   SOLVE, not in QA. See [SOLVE post-processing](../solve_times_nz/postprocessing.md)
   for where summaries are written and [PUBLISH releases](../publish_times_nz/index.md)
   for how they are packaged. The summary needs a `Period`
   (integer year), `Unit` and `Value` column, plus a grouping column if you want
   a breakdown.
2. **Add a `MetricSpec`** to the relevant page in `report/metrics.py`:

   ```python
   MetricSpec(
       "gas-supply-source",                          # unique key, used in anchors and the CSV
       "Natural gas supply by source",               # heading
       "supply/natural_gas_supply_by_source",        # summaries/<this>.csv
       "Supply source",                              # grouping column, or None for a total
       "PJ",                                         # expected unit
   )
   ```

   Add `filters={"Fuel": "Diesel"}` as a sixth argument to select rows from a
   shared table. The expected unit is checked, and a mismatch is an error.
3. **Run the report and the tests.** The page, chart, table, Summary entry (for
   ungrouped metrics) and CSV rows are all produced from the spec.

New pages need an entry in `PAGES` with a URL-safe key and a title. Do not
calculate, convert or fill values in QA. If a figure needs adjusting, fix it in
the SOLVE summary.
