# SOLVE-TIMES-NZ: proposed case-build and solve workflow

`SOLVE-TIMES-NZ` should be a separate, reproducible build-and-run module. Its
job is to turn an explicitly selected set of TIMES Excel workbooks generated by
`PREPARE-TIMES-NZ` into a solvable VEDA/TIMES case, run that case using Windows
GAMS/CPLEX, and bring the results back to Linux for inspection.

It should not edit Excel workbooks, DD files, or solver results in place.
The source workbooks and case definitions are inputs; every runnable case is a
generated artefact.

## Scope and boundary

The current `xl2times` command can produce DD files directly:

```bash
xl2times <excel-files-or-input-directory> --dd --output_dir <case-directory>
```

With `--dd`, xl2times writes three DD files:

- `ts.dd`: the `ALL_TS` set;
- `milestonyr.dd`: the `MILESTONYR` set;
- `output.dd`: all remaining TIMES sets and parameters.

It also writes `raw_tables.txt` and `merged_tables.txt` when an output
directory is supplied. These are useful diagnostics, but are not consumed by
the TIMES generator.

xl2times does *not* produce a VEDA/TIMES `.run` program, run GAMS, or produce
VEDA result (`.vd`) files. It also does not bundle the TIMES generator.
`SOLVE-TIMES-NZ` must supply the run program from a project template and
reference the generator and Windows solve tools as external, versioned
installations.

### xl2times compatibility contract

The supported converter baseline is `xl2times==0.3.0` with `pandas<3`.
`pandas<3` is required because xl2times 0.3.0 is incompatible with the
Arrow-backed string behaviour selected by pandas 3. The converter must be a
direct runtime dependency of `SOLVE-TIMES-NZ`, pinned in the root workspace
lockfile; it must not be an unpinned executable on `PATH`.

TIMES-NZ also requires a small, project-owned compatibility wrapper exposed as
`xl2times-fixed`. It must leave installed xl2times and Excel inputs unchanged,
retain references to the original functions, and apply these four scoped
runtime hooks immediately before delegating to the ordinary xl2times CLI:

1. add blank optional `description` columns to process and commodity dataframes
   before wildcard processing;
2. permit only a `0 -> 0` demand-driver transition by treating its ratio as
   one, while rejecting `0 -> non-zero` restarts;
3. process `~UC_T` region sets before the complete model-region set exists,
   expanding only a generic `UC_FLO` term across one declared `R_E` or `R_S`
   set and preserving explicitly regional terms;
4. append deduplicated `model.implied_topology` rows to the exported `Topology`
   dictionary so ENV-targeted `FLO_EMIS` links reach the TIMES `TOP` table.

The reference implementation and tests are currently held at the repository
root as `cli.py` and `test_cli.py`. They must be ported into
`SOLVE-TIMES-NZ/src/solve_times_nz/` and its test suite as the
`xl2times-fixed` console-script entry point. The reference tests cover optional
descriptions, zero-demand continuation/restart, and implied environmental
topology; add a focused multi-region `UC_FLO` test before implementing
`build`. The issue log and a successful `steady-v309xl2times-test` solve
artefact are evidence for the intended behaviour, but are not a substitute for
versioned tests.

## Recommended repository layout

```text
SOLVE-TIMES-NZ/
  cases/                         # versioned case manifests
    steady.toml
    shift.toml
    experiments/
      steady_shift_carbon.toml
  config/
    input-groups.toml            # versioned workbook groups, maintained by modellers
    solve.local.toml             # ignored: local executor paths/licensing setup
    solve.local.example.toml     # versioned example of local bindings
  templates/
    times.run.template           # generic, path-independent TIMES run template
    cplex.opt                    # optional, versioned solver options
  src/solve_times_nz/
    build_case.py
    xl2times_compat.py           # project-owned xl2times-fixed wrapper (from root cli.py reference)
    run_windows.py
  build/                         # ignored: generated cases and copied results
    cases/<case-id>/
    results/<case-id>/
```

For now, the canonical input root is `PREPARE-TIMES-NZ/output`, populated by
the preparation pipeline. The builder defaults to that path relative to the
repository root, while retaining `--input-root` for a future relocated or
external source tree. The input root is generated and may not exist in a fresh
clone, so `resolve` and `build` must fail clearly until PREPARE has produced
the selected workbooks.

Do not copy all source Excel files into every generated case: after xl2times
has created the DDs, the Windows solve only needs the generated case directory.

## Declarative case definitions

Use TOML. It is strict, native to Python (`tomllib`), and a good fit for
mostly structured configuration.

Split workbook selection into named input groups. Keep groups narrow and
semantic, rather than using one broad wildcard for every scenario workbook.
Groups may also be composite: an `includes` list can name other groups. This
lets a case select a useful bundle such as `steady`, while retaining small,
reusable groups for each input family.

```toml
# config/input-groups.toml
#
# Paths and glob patterns are relative to PREPARE-TIMES-NZ/output by default.
# Populate the groups below with the authoritative workbook selection for each
# case. Keep one scenario family per group; do not mix Steady and Shift files
# in a group unless the case explicitly requires that combination.

[groups.base]
files = []

[groups.steady]
includes = ["base"]
files = []

[groups.shift]
includes = ["base"]
files = []

# Add small reusable groups for individual input families, then include them
# from `steady`, `shift`, or an experiment-specific composite group.
#
# [groups.carbon_steady]
# files = ["SuppXLS/Scen_Carbon_Steady.xlsx"]
#
# [groups.steady]
# includes = ["base", "carbon_steady"]
```

Wildcards are expanded by `SOLVE-TIMES-NZ`, relative to the input root;
they are not expanded by TOML itself. The builder must sort and de-duplicate
matches, recursively expand `includes`, and save the fully resolved paths in
the build manifest. It must fail clearly for a missing group, a required
pattern that matches nothing, or an inclusion cycle such as `a → b → a`.

A normal case selects named groups:

```toml
# cases/steady.toml
name = "steady"
groups = ["steady"]

[xl2times]
regions = ["NI", "SI"]
include_dummy_imports = false

[times]
solver = "cplex"
reslim = 50000

[solve]
toolchain = "veda-times-4.8.3"
```

Experiments inherit and make intentional substitutions:

```toml
# cases/experiments/steady_shift_carbon.toml
name = "steady-shift-carbon"
extends = "steady"
remove_groups = ["carbon_steady"]
add_groups = ["carbon_shift"]
```

Support `add_files` and `remove_files` as an escape hatch, but prefer named
groups. `remove_groups = ["carbon_steady"]` communicates intent and remains
stable if the group gains a second workbook.

## Build a case

The builder should accept a case manifest and input root, for example:

```bash
solve-times-nz build cases/steady.toml \
  --input-root PREPARE-TIMES-NZ/output \
  --output build/cases/steady
```

Its steps should be:

1. Locate the input root (defaulting to `PREPARE-TIMES-NZ/output`), load the
   manifest, resolve inheritance, then recursively resolve input
   groups (including composite-group `includes`) into one ordered,
   de-duplicated list of `.xlsx`/`.xlsm` files.
2. Validate the selection before conversion. Useful initial rules are:
   - no input file appears twice;
   - every declared pattern has at least one match;
   - exactly one member of mutually exclusive groups (for example `steady` or
     `shift`) is present;
   - no filename labelled `Steady` and `Shift` is selected for the same
     scenario family unless that mixture is explicitly allowed.
3. Replace the requested generated case directory. Generated DD inputs must
   always be reproducible from the selected workbooks and configuration, so do
   not retain or edit prior contents in place. A simple initial convention is
   `build/cases/<case-name>/`; a stronger one adds a short content hash or
   timestamp when multiple builds must be retained for comparison.
4. Invoke `xl2times-fixed` with explicit paths, not with the whole input
   directory:

   ```bash
   xl2times-fixed file1.xlsx file2.xlsx ... \
     --dd --output_dir build/cases/steady
   ```
5. Render `<case-name>.run` from `templates/times.run.template`, substituting only
   case-level options such as solver, resource limit, validation/reduction
   switches, and the model name. Copy `cplex.opt` only if the selected solver
   configuration uses it.
6. Write `manifest.json` into the case directory with the case name, resolved
   inputs, SHA-256 hashes of inputs, xl2times, compatibility-wrapper, pandas,
   and Python versions, command line, Git revision, template hash, build time,
   and requested solver configuration.
7. Mark the case as complete only when `ts.dd`, `milestonyr.dd`, `output.dd`,
   the `.run` file, and the manifest all exist.

The generated case directory should look like:

```text
build/cases/steady/
  ts.dd
  output.dd
  milestonyr.dd
  steady.run
  cplex.opt                  # only when applicable
  raw_tables.txt             # diagnostic
  merged_tables.txt          # diagnostic
  manifest.json
```

## Generic run template

Create one project-owned generic run template now; do not depend forever on a
historical `times-allscen.run`. It should encode the standard generator
protocol for the specific `GAMS_SrcTIMES` version in use:

1. Set GAMS options and the selected solver (`option LP=cplex`, where
   appropriate).
2. Set standard TIMES switches (`VALIDATE`, `REDUCE`, `SOLVE_NOW`, etc.).
3. `$BATINCLUDE ts.dd` before TIMES initialization, because time-slice order
   matters.
4. Include `initsys.mod` and `initmty.mod` from the external TIMES generator
   source directory.
5. `$BATINCLUDE output.dd`.
6. `$BATINCLUDE milestonyr.dd`.
7. `$BATINCLUDE maindrv.mod mod` to generate and solve the model.

The exact boilerplate should be extracted and tested once against the selected
generator version (currently, for the reference case, `GAMS_SrcTIMES.v4.8.3`).
`steady-v309xl2times-test/steady-v309xl2times-test.run` is a useful reference
for the GAMS options and generator protocol, but it includes VEDA's many
per-workbook DD files. It must not be copied as the template: the first
xl2times integration test must establish and verify the include order for the
three combined files (`ts.dd`, `output.dd`, and `milestonyr.dd`). The template
should then use those relative includes and receive the generator source
directory through the Windows launcher/GAMS input directory mechanism. Do not
embed a user-specific `C:\Users\...` path in the template.

## Execution boundary

The Windows GAMS/CPLEX licence must be used by native Windows GAMS. A Linux/WSL
GAMS installation cannot use a licence issued for Windows.

Store machine-specific executor bindings outside version control. A toolchain
is selected by a versioned case manifest; an executor describes where that
toolchain is available on one machine. This keeps the case portable between a
Windows-mounted installation today and a later native WSL/Linux installation.

```toml
# config/solve.local.toml -- ignored
[executors.windows_veda]
kind = "windows"
toolchains = ["veda-times-4.8.3"]
staging_root = "/mnt/c/TIMES-NZ/runs"
gams_system_dir = "C:\\GAMS\\44"
times_source_dir = "C:\\Users\\<user>\\Veda\\GAMS_SrcTIMES.v4.8.3"
launcher = "C:\\Users\\<user>\\Veda\\GAMS_SrcTIMES.v4.8.3\\VT_GAMS"
result_exporter = "C:\\Users\\<user>\\Veda\\GAMS_SrcTIMES.v4.8.3\\GDX2VEDA"
```

`solve-times-nz stage build/cases/steady --executor windows_veda` copies the
complete generated case to a unique directory under the configured staging root
and refuses to overwrite an existing staged run. Once the reference launcher
invocation is confirmed, `solve` should:

1. Verify that the generated case is complete and has not changed since its
   manifest was written.
2. Copy the case directory to a new Windows staging directory such as
   `GAMS_WrkTIMES\steady-<build-id>`. Avoid overwriting an existing case or
   using destructive mirror operations by default.
3. Invoke the standard Windows TIMES launcher (`VT_GAMS`, or an equivalent
   project-owned wrapper) with that working directory, the configured TIMES
   source/version, and the case `.run` file.
4. After a successful GAMS solve, invoke the VEDA `GDX2VEDA` exporter against
   the solved GDX, using the matching `times2veda.vdd` mapping from the TIMES
   generator/source installation. This is the required step that creates the
   VEDA `.vd` result file consumed by the existing post-processing. Depending
   on the installed exporter, it may also create companion `.vde`, `.vds`, and
   `.vdt` files; preserve them as one result package.
5. Capture both Windows command lines, exit codes, start/end times, and console
   output into a solver-run manifest.
6. Treat a non-zero process exit code, GAMS compilation error, GDX2VEDA error,
   or absent expected `.vd` result as a failed solve.
   expected solution artefact as a failed solve.

The first implementation can use a shared Windows drive mounted in WSL (for
example `/mnt/c/...`) rather than a network transfer. If the repository lives
inside the WSL filesystem, copy only the completed case directory to the
Windows staging root before running; native Windows tools are more reliable on
native Windows paths than on `\\wsl$` paths.

## Return and preserve results

After a solve, copy results back to:

```text
build/results/<case-id>/
```

Preserve at least:

- GAMS listing (`.lst`) and run log;
- GAMS status/error files (`.log`, `.sta`, where produced);
- solution GDX and any `GAMSSAVE` artefacts needed to inspect it;
- the exported VEDA result package (`.vd` and any `.vde`, `.vds`, `.vdt`
  companions) used by post-processing;
- the Windows-run manifest and a copy of the original case `manifest.json`.

Large binary results may be ignored by Git or moved to an artefact store, but
their hashes and the complete case definition should remain versioned. The
important invariant is that a returned result can always identify the exact
Excel inputs, converter version, DD files, run template, TIMES source version,
and solver configuration that produced it.

## Suggested implementation order

1. Implement TOML loading, named input groups, inheritance, and a `resolve`
   command that only prints the selected workbooks.
2. Add the validations and write `manifest.json`.
3. Port the root `cli.py` and `test_cli.py` references into the
   `xl2times-fixed` compatibility-wrapper and test suite; add the missing
   multi-region `UC_FLO` regression test, then pin `xl2times==0.3.0` and
   `pandas<3` in the workspace.
4. Add `build`, calling `xl2times-fixed` with `--dd`; inspect the resulting
   DDs before attempting a solve.
5. Establish and test one generic `.run` template against a tiny case.
6. Add Windows staging and a launcher wrapper.
7. Add result collection and a simple `status` command.

Start with one known case (for example a steady baseline) and one deliberately
small experiment. Only generalize scenario options after both can be rebuilt
and solved from a clean working directory.
